System operationuser·product·stress API 운영 및 모니터링 (EKS)

Golang/Gin으로 개발된 user·product·stress 어플리케이션을 EKS(EC2 c5.large)와 Multi-AZ RDS, S3로 배포하고, 단일 엔드포인트로 목표 서비스 수준을 만족하도록 트래픽을 처리하며 모니터링·로깅으로 장애를 감지해 저비용으로 운영하는 과제입니다.

VPCEKSEC2ECRRDSS3CloudFrontWAFGolang
📝 채점기준 보기

개요

개발된 어플리케이션을 배포하여 사용자들에게 서비스를 제공하는 시스템을 구축하고 운영을 위한 모니터링 시스템을 구축합니다. 목표로 설정한 서비스 수준을 만족하도록 트래픽을 처리해야 하며, 구축한 시스템에 발생할 수 있는 장애와 오류를 빠르게 감지하여 최적의 사용자 경험을 제공하도록 시스템을 운영해야 합니다. 동시에 최대한 저비용으로 시스템을 운영할 수 있도록 합니다.

사용 기술

필수 Software Stack

분류 항목
AWS VPC, EKS, EC2, ECR, RDS, S3
개발언어/프레임워크 Golang / Gin

사용 가능 Software Stack

분류 항목
AWS ELB, API Gateway, CloudFront, R53, Cloudwatch, WAF
개발언어/프레임워크 Docker

선수 유의사항

  1. 선수의 계정에는 비용제한이 존재하며, 이보다 더 높게 과금될 시 계정 사용이 불가능할 수 있습니다.
  2. 문제에 제시된 괄호박스 <>는 변수를 뜻함으로 선수가 적절히 변경하여 사용해야 합니다.
  3. 과제 종료 시 진행 중인 테스트를 모두 종료하여 서버에 부하가 발생 하지 않도록 합니다.
  4. 별도 언급이 없는 경우, ap-northeast-2 리전에 리소스를 생성하도록 합니다.
  5. 1페이지의 다이어그램은 구성을 추상적으로 표현한 그림으로, 세부적인 구성은 아래의 요구사항을 만족시킬 수 있도록 합니다. (ex. 서브넷이 2개 이상 존재할 수 있습니다.)
  6. 모든 리소스의 이름, 태그, 변수는 대소문자를 구분합니다.
  7. 문제에서 주어지지 않는 값들은 AWS Well-Architected Framework 6 pillars를 기준으로 적절한 값을 설정해야 합니다.
  8. 불필요한 리소스를 생성한 경우 감점의 요인이 될 수 있습니다.
    (e.g. 미사용 EC2, VPC 추가, 다른 리전 리소스 생성 등)
  9. DB 및 모든 리소스에 대해 정해진 인스턴스 타입, CPU, Memory 크기와 대수를 지키지 않으면 불이익이 있을 수 있습니다. (미사용도 모두 포함)
  10. 모든 시간은 KST(UTC+9) 타임존을 사용합니다.
  11. 컴퓨팅 타입은 EC2 인스턴스만 사용하도록 합니다. 어떠한 목적으로든 Fargate와 Lambda를 사용할 수 없습니다.
  12. 경기 시작 1시간 후부터 Fargate와 Lambda 등 EC2를 제외한 컴퓨팅 리소스가 하나라도 존재할 경우, 성능 항목과 비용 항목에 대한 부정 행위로 간주하여 채점항목 3번과 4번을 모두 0점 처리합니다. 해당 두 항목의 배점은 총 24점이므로, Amazon Q 등에서 복사한 명령어를 실행하거나 다른 스택을 배포하는 과정에서 실수로 관련 리소스가 생성되지 않도록 각별히 주의해야 합니다. 사용자 플랫폼에서도 필요한 참고 정보를 확인할 수 있으므로, EC2 이외의 컴퓨팅 리소스는 절대 생성하지 않도록 합니다.
  13. RDS 및 Aurora Database는 문제지에 명시된 대로 db.t3.micro 타입만 사용할 수 있으며, Primary Instance는 1대만 생성할 수 있습니다. 어떠한 목적으로도 Read Replica를 생성하거나 1대를 초과하는 DB 인스턴스를 구성할 수 없으며, db.t3.micro 이외의 인스턴스 타입 사용 및 여러 개의 DB 클러스터 생성 또한 금지됩니다. 해당 사항 적발 시 채점항목 3번과 4번을 모두 0점 처리합니다. 해당 두 항목의 배점은 총 24점이므로, Amazon Q 등에서 복사한 명령어를 실행하거나 다른 스택을 배포하는 과정에서 실수로 관련 리소스가 생성되지 않도록 각별히 주의해야 합니다.
참고

원문 불일치: 위 12번은 Fargate·Lambda 등 EC2 외 컴퓨팅 리소스가 존재할 경우 채점항목 3번과 4번을 0점 처리한다고 되어 있으나, 채점지 0. 사전준비 4번은 "Lambda 사용과 관련해 부적절한 형태로 사용 시 전체 0점 처리"로 되어 있습니다.

3. 관계형 데이터베이스

  • user, product 어플리케이션은 관계형 데이터베이스를 사용하며 읽기, 쓰기 작업이 모두 가능해야 합니다.
  • 어플리케이션은 MySQL Community 엔진을 지원합니다.
  • DB 인스턴스는 최소한으로 운영합니다. 요구사항을 지키지 않으면 불이익이 있을 수 있습니다.
항목 값
DB identifier apdev-rds-instance
Deployment options Multi-AZ DB instance
DB instance class db.t3.micro
Storage type General Purpose SSD (gp3)
Engine MySQL Community 8.0

아래의 명령어를 참고하여 테이블을 생성할 수 있습니다.

CREATE TABLE user (
    id               VARCHAR(255)    NOT NULL,
    username         VARCHAR(255)    NOT NULL,
    email            VARCHAR(255)    NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_username (username)
);

CREATE TABLE product (
    id               VARCHAR(255)    NOT NULL,
    name             VARCHAR(255)    NOT NULL,
    price            FLOAT(8)        NOT NULL,
    image_path       VARCHAR(500)    DEFAULT NULL,
    PRIMARY KEY (id)
);
  • 정상적인 동작을 위해서 load_user.dump 파일을 사용하여 데이터를 삽입해야 하며, 삽입한 데이터는 임의로 수정하거나 삭제하지 않도록 합니다.
  • 발생하는 트래픽 외 임의의 데이터를 삽입하면 성능 저하가 생길 수 있으므로 주의하도록 합니다.
  • 어플리케이션 동작과 트래픽 패턴에 맞게 테이블 구조 재설계가 필요할 수 있습니다.

4. 웹 어플리케이션

  • user, product, stress 총 3 개의 어플리케이션이 있습니다.
  • 제공된 binary는 x86기반 EC2의 Amazon Linux 2023 에서 빌드하고 동작을 확인하였습니다. go version은 go1.22.2 linux/amd64 입니다.
  • 어플리케이션 실행 시 바인딩되는 포트는 TCP/8080 입니다.
  • 모든 어플리케이션에서 발생하는 로그들은 stdout 또는 stderr로 출력됩니다.
  • 요청 및 응답의 변조를 방지하기 위해 모든 애플리케이션의 요청에는 requestid와 uuid 값이 포함됩니다. POST, PUT 메소드의 경우 Request Body에 포함되며, GET 메소드의 경우 Query String에 포함됩니다. 자세한 요청 형식은 각 애플리케이션별 동작 예시를 참고합니다.
  • 정상적인 요청에 대해 Request 및 Response를 변조하여 불이익을 받지 않도록 합니다.
  • 채점 시 사용되는 응답시간 및 응답코드는 모두 클라이언트 도착 기준입니다.

5. S3

  • 제품의 이미지를 제공하기 위해 오브젝트 스토리지인 S3 를 구성합니다.
  • 버킷 이름은 자유롭게 명명하도록 하며, 어플리케이션을 배포한 리전에 버킷을 생성하는 것을 권장합니다.
  • product 어플리케이션에서 이미지 업로드가 가능하도록 설정해야합니다.
  • 해당 버킷에 저장되어 있는 오브젝트들은 어플리케이션과 동일한 엔드포인트로 인터넷 사용자들에게 제공되어야 합니다. 최종적으로 인터넷 사용자는 어플리케이션과 동일한 엔드포인트의 /images/<object path> 경로 GET 요청으로 이미지를 다운로드 받을 수 있어야 합니다.
  • 경기 시작 1시간 후부터 트래픽이 발생하며, product 애플리케이션의 동작에 따른 이미지 업로드와 이미지 다운로드 시나리오를 포함한 모의 트래픽이 함께 발생합니다. 엔드포인트 설정에 대한 자세한 내용은 6. 트래픽 처리 내용을 참고합니다.
  • 이미지 다운로드는 최소한의 가용성을 위해 5초 이내의 응답시간을 보장하고자 하며, 서비스 수준 목표 또한 동일하게 설정하였습니다. 해당 기준으로 서비스 수준을 측정하고 정적 컨텐츠를 제공할 수 있도록 합니다.

6. 트래픽 처리

  • 어플리케이션을 배포하고 외부 사용자들에게 서비스를 제공할 수 있도록 시스템을 구축합니다.
  • 컨테이너를 활용해야 하며 컨테이너 오케스트레이션 툴로는 EKS를 사용합니다. ECS를 사용할 수 없습니다.
  • 컨테이너 이미지 레포지토리로는 ECR을 사용할 수 있으며 컨테이너 호스팅을 위한 컴퓨팅 리소스는 EC2를 사용합니다.
  • EC2 인스턴스는 c5.large 타입만을 사용하도록 하며, 트래픽 처리를 위해 최소한의 리소스만을 사용하도록 합니다. 다른 인스턴스 타입을 사용하거나 과도한 리소스를 사용할 경우 감점의 원인이 될 수 있습니다.
  • 트래픽 처리를 위해 사용자에게 제공되는 엔드포인트를 하나로 단일화하도록 합니다.
  • 경기 시작 1시간 뒤부터 트래픽이 발생하며 채점 플랫폼에 입력한 엔드포인트로 선수의 시스템에 주입됩니다. 경기 중 발생하는 트래픽을 목표 서비스 수준에 만족하도록 처리하세요.
  • 모니터링 환경과 로깅 솔루션을 구축하여 로그 분석, 트래픽 패턴 분석, 시스템 개선, 시스템 장애/오류 감지 및 대처를 수행해야 합니다.
  • 본인의 엔드포인트를 타인에게 노출하여 불이익을 받는일이 없도록 합니다.
  • 채점 플랫폼에 입력하는 형식은 프로토콜 및 주소(IP/DNS)이며 경로를 적어선 안됩니다.
  • 제출하는 Endpoint는 선수의 AWS 계정에 존재하는 자원이 가지는 AWS 도메인을 사용합니다. 외부 시스템의 DNS를 입력하거나, 선수가 구매한 별도 DNS의 레코드를 지정해서는 안됩니다.

정상 예시 https://example.org
잘못된 예시(1) example.org (프로토콜 누락)
잘못된 예시(2) https://example.org/v1/ (경로 기입)
  • 서비스 중단 없이 안정적으로 서비스를 제공할 수 있도록 가용성 확보합니다. 이를 고려하여 시스템을 설계하고 구축한 뒤 운영할 수 있도록 합니다.
  • 사용자에게 제공하는 엔드포인트로의 비정상적인 요청은 Block 하도록 하며, 403 응답코드를 내려주도록 합니다. 단, 제공하는 API 외의 요청은 404 응답코드를 내려주도록 합니다.

  • /v1/none 으로의 비정상 요청: 404 응답코드
