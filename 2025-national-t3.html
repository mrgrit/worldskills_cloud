System Operation

개발된 user, product, stress 어플리케이션을 ECS(EC2)로 배포해 주입되는 트래픽을 목표 서비스 수준에 맞게 처리하고, 모니터링 시스템을 구축해 장애와 오류를 빠르게 감지하며 최대한 저비용으로 운영하는 과제입니다.

VPCECSEC2ECRRDSDynamoDBELBCloudFrontWAFGolang
📝 채점기준 보기

개요

개발된 어플리케이션을 배포하여 사용자들에게 서비스를 제공하는 시스템을 구축하고 운영을 위한 모니터링 시스템을 구축합니다. 목표로 설정한 서비스 수준을 만족하도록 트래픽을 처리해야 하며, 구축한 시스템에 발생할 수 있는 장애와 오류를 빠르게 감지하여 최적의 사용자 경험을 제공하도록 시스템을 운영해야 합니다. 동시에 최대한 저비용으로 시스템을 운영할 수 있도록 합니다.

사용 기술

분류 항목
AWS (필수) VPC, ECS, EC2, ECR, RDS, DynamoDB
개발언어/프레임워크 (필수) Golang / Gin
AWS (사용 가능) ELB, API Gateway, CloudFront, R53, S3, CloudWatch, WAF
개발언어/프레임워크 (사용 가능) Docker

선수 유의사항

  1. 선수의 계정에는 비용제한이 존재하며, 이보다 더 높게 과금될 시 계정 사용이 불가능할 수 있습니다.
  2. 문제에 제시된 괄호박스 <>는 변수를 뜻함으로 선수가 적절히 변경하여 사용해야 합니다.
  3. 과제 종료 시 진행 중인 테스트를 모두 종료하여 서버에 부하가 발생 하지 않도록 합니다.
  4. 글로벌 리소스를 제외한 모든 리소스는 ap-northeast-2 만 사용해야 합니다.
  5. 1페이지의 다이어그램은 구성을 추상적으로 표현한 그림으로, 세부적인 구성은 아래의 요구사항을 만족시킬 수 있도록 합니다. (ex. 서브넷이 2개 이상 존재할 수 있습니다.)
  6. 모든 리소스의 이름, 태그, 변수는 대소문자를 구분합니다.
  7. 문제에서 주어지지 않는 값들은 AWS Well-Architected Framework 6 pillars를 기준으로 적절한 값을 설정해야 합니다.
  8. 불필요한 리소스를 생성한 경우 감점의 요인이 될 수 있습니다. (e.g. 미사용 EC2, VPC 추가, 다른 리전 리소스 생성 등)
  9. DB 및 모든 리소스에 대해 정해진 인스턴스 타입, CPU, Memory 크기와 대수를 지키지 않으면 불이익이 있을 수 있습니다. (미사용도 모두 포함)
  10. 모든 시간은 KST(UTC+9) 타임존을 사용합니다.
  11. 컴퓨팅 타입은 EC2 인스턴스만 사용하도록 합니다. 어떠한 목적으로든 Fargate와 Lambda를 사용할 수 없습니다.
  12. 대회 플랫폼에 Endpoint를 올바르게 입력하지 않거나, 선수의 서버로 요청 차단이 되면 감점의 요인이 될 수 있습니다. Inbound를 열거나 적절한 조치를 하도록 합니다.
  13. Endpoint의 프로토콜은 HTTP 혹은 HTTPS만 사용합니다.
  14. 대회 플랫폼의 Score Board에서 제공하는 수치는 샘플링 된 값이며 결과 반영까지 약간의 지연이 있을 수 있습니다. 채점 시에는 전체 데이터를 이용해 채점을 진행합니다.
  15. EC2 비용 집계는 스크립트에서 조회된 Running 상태의 인스턴스가 대상입니다.
  16. 대회 플랫폼에서 제공하는 Score Board의 각 요소들은 다음을 의미합니다.
    • Infra: 평균적으로 사용한 인스턴스의 개수. (c5.large가 아닌 경우 패널티 부여)
    • Response(total): 현재 선수에게 주입된 API 요청 및 응답 수.
    • Response(2xx): 현재 선수에게 주입된 API 요청 중 2xx 코드 응답 수.
    • Response(3xx): 현재 선수에게 주입된 API 요청 중 3xx 코드 응답 수.
    • Response(4xx): 현재 선수에게 주입된 API 요청 중 4xx 코드 응답 수.
    • Response(5xx): 현재 선수에게 주입된 API 요청 중 5xx 코드 응답 수.
    • Response(err): 현재 선수에게 주입된 API 요청 중 Timeout과 같은 비정상 응답 수.
  17. 아래의 허용되지 않은 리소스를 생성하면 첫 적발 시 1점 감점에, 두 번째 적발 시 비용 관련 점수 0점 처리됩니다.
    • 서울 지역 외 다른 지역에 EC2 등 컴퓨팅 리소스, RDS(Aurora)를 만드는 경우.
    • 지역 상관없이 Lambda 리소스를 만드는 경우. 서울 지역에 만드는 경우도 감점 대상.
    • db.t3.micro가 아닌 다른 RDS(Aurora) 타입을 사용하는 경우.
    • RDS(Aurora)를 두 대 이상 쓰는 경우.
참고

채점기준(0. 사전준비 3)은 이 감점을 "첫 적발 시 비용 관련 점수 최대 1점 감점, 두 번째 적발 시 비용 관련 점수 0점(비용 점수는 0점 미만으로 내려가지 않음)"으로 규정하고, 컴퓨팅 관련 리소스의 예로 EC2, ECS, EKS, Fargate, Lambda, RDS, Elastic Beanstalk, Lightsail, Batch 등을 듭니다.

3. 관계형 데이터베이스

  • user 어플리케이션은 관계형 데이터베이스를 사용하며 읽기, 쓰기 작업이 모두 가능해야 합니다.
  • 어플리케이션은 MySQL Community 엔진을 지원합니다.
  • DB 인스턴스는 최소한으로 운영합니다.
  • 데이터베이스는 Primary 한 대만 사용하며 Read Replica는 생성하지 않습니다.
  • 다른 지역에 데이터베이스를 추가하면 안됩니다.
항목 값
DB identifier apdev-rds-instance
Deployment options Multi-AZ DB instance
DB instance class db.t3.micro
Storage type General Purpose SSD (gp3)
Engine MySQL Community 8.0

아래의 명령어를 참고하여 테이블을 생성할 수 있습니다. 스키마 변경은 가능 하지만 선수의 서비스에 영향이 가지 않도록 주의하세요.

CREATE TABLE user (
    id               VARCHAR(255)    NOT NULL,
    username         VARCHAR(255)    NOT NULL,
    email            VARCHAR(255)    NOT NULL,
    status_message   VARCHAR(255)    NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_username (username)
);
  • 정상적인 동작을 위해서 load_user.dump 파일을 사용하여 데이터를 삽입해야 하며, 삽입한 데이터는 임의로 수정하거나 삭제하지 않도록 합니다.
  • 발생하는 트래픽 외 임의의 데이터를 삽입하면 성능 저하가 생길 수 있으므로 주의하도록 합니다.
  • 어플리케이션 동작과 트래픽 패턴에 맞게 테이블 구조 재설계가 필요할 수 있습니다.

4. DynamoDB

  • product 어플리케이션은 DynamoDB를 사용하며 읽기, 쓰기 작업이 모두 가능해야합니다.
  • 테이블은 1개만 생성하도록 하며, 테이블에 저장하는 데이터의 예제 포맷은 다음과 같습니다.
  • 어플리케이션 동작과 트래픽 패턴에 맞게 PK, SK, Index의 설계가 필요할 수 있습니다.
  • DynamoDB의 스케일(Capacity)은 별도 제한이 없으나 너무 과도한 비용이 나오지 않도록 하세요.
Key Data Type Description
id string product 고유값
name string product 이름
price Number product 가격

5. 웹 어플리케이션

  • user, product, stress 총 3 개의 어플리케이션이 있습니다.
  • 제공된 binary는 x86기반 EC2의 Amazon Linux 2023 에서 빌드하고 동작을 확인하였습니다.
  • go version은 go1.22.2 linux/amd64 입니다.
  • 어플리케이션 실행 시 바인딩되는 포트는 TCP/8080 입니다.
  • 모든 어플리케이션은 access log를 stdout, stderr로 출력합니다.
  • 모든 어플리케이션은 변조 방지를 위해 Request 요청의 쿼리스트링이나 바디에 requestid, uuid가 추가됩니다.
  • 정상적인 요청에 대해 Request 및 Response를 변조하여 불이익을 받지 않도록 합니다.
  • 채점 시 사용되는 응답시간 및 코드는 모두 클라이언트 도착 기준입니다.

6. 트래픽 처리

  • 어플리케이션을 배포하고 외부 사용자들에게 서비스를 제공할 수 있도록 시스템을 구축합니다.
  • 컨테이너를 활용해야 하며 컨테이너 오케스트레이션 툴로는 ECS를 사용합니다. EKS를 사용할 수 없습니다.
  • 컨테이너 이미지 레포지토리로는 ECR을 사용할 수 있으며 컨테이너 호스팅을 위한 컴퓨팅 리소스는 EC2를 사용합니다.
  • EC2 인스턴스는 c5.large 타입만을 사용하도록 하며, 트래픽 처리를 위해 최소한의 리소스만을 사용하도록 합니다.
  • 더 저렴한 인스턴스를 포함해 다른 인스턴스 타입을 사용하거나 과도한 리소스를 사용할 경우 감점의 원인이 될 수 있습니다.
  • 트래픽 처리를 위해 사용자에게 제공되는 엔드포인트를 하나로 단일화하도록 합니다.
  • 경기 시작 1시간 뒤부터 트래픽이 발생하며 채점 플랫폼에 입력한 엔드포인트로 선수의 시스템에 주입됩니다.
  • 경기 중 발생하는 트래픽을 목표 서비스 수준에 만족하도록 처리하세요.
  • 모니터링 환경과 로깅 솔루션을 구축하여 로그 분석, 트래픽 패턴 분석, 시스템 개선, 시스템 장애/오류 감지 및 대처를 수행해야 합니다.
  • 본인의 엔드포인트를 타인에게 노출하여 불이익을 받는일이 없도록 합니다.
  • 채점 플랫폼에 입력하는 형식은 프로토콜 및 주소(IP/DNS)이며 경로를 적어선 안됩니다.
    • 정상 예시: https://example.org
    • 잘못된 예시(1): example.org (프로토콜 누락)
    • 잘못된 예시(2): https://example.org/v1/ (경로 기입)
  • 서비스 중단 없이 안정적으로 서비스를 제공할 수 있도록 가용성 확보합니다. 이를 고려하여 시스템을 설계하고 구축한 뒤 운영할 수 있도록 합니다.
  • 사용자에게 제공하는 엔드포인트로의 비정상적인 요청은 Block 하도록 하며, 403 응답코드를 내려주도록 합니다. 단, 제공하는 API 외의 요청은 404 응답코드를 내려주도록 합니다.

예제)

  • /v1/user 으로의 비정상 요청: 403 응답코드
  • /v1/none 으로의 비정상 요청: 404 응답코드
