  4. 과제 종료 전 실행 중인 테스트 및 부하를 중지하여 서버에 문제가 없도록 해야 합니다.
  5. Tag 정보가 맞지 않거나 권한 문제가 생겨 채점이 불가하지 않도록 주의합니다.
  6. 채점을 위한 Bastion을 생성하고, Bastion은 모든 Resource를 Access 할 수 있어야 합니다.
  7. 채점지에 표기된 Bastion 혹은 서버 접근 방법에 대해서 잘 확인할 수 있도록 합니다.
  8. Gtihub Action의 무료 할당량을 소진하여 채점 시 불이익을 받지 않도록 합니다.
  9. 채점지와 문제지 마다 사용하는 Region이 모두 다르니 확인 하도록 합니다.

1) CI/CD

개요

컨테이너에 앱을 배포할 수 있는 CI/CD 파이프라인을 구성합니다. Region은 ap-southeast-1을 사용합니다.

과제 설명

1. ECR

  • Container Image 관리를 효율적으로 하기 위해 전용 Registry를 생성합니다.
  • 제공한 배포 파일(index.html)을 기본 페이지로 설정한 커스텀 이미지를 nginx:latest 기반으로 빌드합니다.
  • 이미지 태그는 vX.X.X 형식(예: v1.0.0)으로 지정하여 버전 관리를 용이하게 합니다.
  • ECR Repository Name: app-repo

2. EKS

  • 컨테이너를 효율적이고 쉽게 관리하기 위해 EKS를 사용합니다.
  • 애플리케이션 Pod들은 “wsc2025”라는 Namespace에서 운영되어야 합니다.
  • Deployment의 이름은 “nginx-deploy”로 지정합니다.
  • 채점하기 전 제공한 배포파일을 사용해 대회 중 생성한 image로 Pod를 생성합니다.
항목 값
EKS Cluster Name wsc2025-cluster
EKS Cluster Version 1.32
EKS Node Instance Type t3.medium
EKS NodeGroup Name wsc2025-app-ng
EKS Node Name wsc2025-app-node

3. ELB

  • 애플리케이션 Pod들을 접근할 수 있는 Endpoint를 제공합니다.
  • Endpoint는 외부에서 접근 문제가 없어야 하며, Pod가 재시작 혹은 추가되어도 정상적으로 접근이 되어야 합니다.
  • LoadBalancer Type: ALB
  • LoadBalancer Name: wsc2025-cicd-alb

4. Github

  • 주어진 배포파일인 index.html과 verison 파일은 Repository 최상단에 두고, Kubernetes manifest 파일들을 manifest/ 경로에 생성하며 Deployment를 배포하는 manifest의 이름은 deploy.yaml로 지정합니다.
  • Github Action을 통하여 index.html 파일이 변경 혹은 수정이 된다면 자동으로 Github Action이 동작하며 version 파일을 사용하여 tag를 지정하고 새로운 이미지를 생성합니다.
  • 또한 deploy.yaml의 이미지를 새로운 이미지로 변경합니다.
  • 단 Github Action은 index.html이 변경되었을 때만 동작해야 합니다.
  • 채점 시 Github Action의 Job이 모두 성공 했는지 확인하며, 커밋 후 빌드 완료까지 제한시간은 5분입니다.
  • Repository Name: wsc2025-argocd-repo
  • Repository Type: Public

5. ArgoCD

  • Github Action을 통해 새로운 Image가 생성되면 새로운 Image를 사용한 Pod들이 5분 안에 생성되어야 합니다.
  • github Repository에서 코드를 변경하는 것이 아닌 관리자가 다른 방법으로 이미지를 변경할시 자동으로 복구되어야 합니다. (채점시 Github Action의 Job이 끝난 후 5분안에 html 페이지가 로딩 되어야 합니다.)
  • ArgoCD App Name: wsc2025-argo-app

2) Storage data protect

개요

Object Storage인 S3에 저장되는 데이터 보호를 위한 솔루션을 구성합니다. Region은 ap-northeast-2을 사용합니다.

과제 설명

1. S3

  • 민감한 데이터를 가지고 있는 파일들을 관리하기 위해 S3를 사용합니다.
  • S3에는 /masked라는 prefix와 /incoming이라는 prefix를 생성합니다.
  • 주어진 배포파일은 /incoming prefix에 전부 업로드하도록 합니다.
  • S3 Bucket Name: wsc2025-sensitive-<임의의 4개의 영문>

2. Macie

  • S3에 저장된 민감한 데이터를 검색하고 보호하기 위해 Amazon Macie를 사용합니다.
  • Macie를 활용하여 배포 파일 내의 모든 민감한 정보를 정확히 감지할 수 있어야 하며, 감지 기준은 아래 표를 참고합니다.
  • Job 생성 시 S3 버킷 내 masked 접두어(prefix)를 가진 객체들에 대해서만 민감한 데이터를 감지하도록 설정하고, Job은 한 번만 실행되도록 구성해야 합니다.
  • Job Name: wsc2025-sensor-job
주의

채점 시에는 생성해둔 Job을 복사하여 사용하며, 해당 Job이 정상적으로 동작하지 않을 경우 감점 등의 불이익이 발생할 수 있습니다.

3. Lambda

  • 민감한 데이터의 유출을 방지하기 위해 AWS Lambda를 사용하여 데이터를 마스킹합니다.
  • Lambda 함수는 S3 버킷의 incoming 접두어(prefix)를 가진 경로에 파일이 업로드되면 자동으로 실행되어, 해당 파일의 민감한 정보를 마스킹한 후 masked 접두어를 가진 경로에 저장해야 합니다.
  • 마스킹 방식에 대한 예시는 아래 표를 참고합니다.
  • Lambda Name: wsc2025-masking-start
민감한 정보 유형 원본 예시 (Maice에서 감지되어야 함) 마스킹 예시 (Maice에서 감지되지 않아야함)
names Crystal White Crystal *****
emails davisjesus@example.org d*********@example.org
phone_numbers 010-7658-5153 010-7658-****
ssns 887-07-7325 887-07-****
card_numbers 4468-6779-7028-4776 4468-6779-7028-****
uuids 665ef2db-cd63-4086-81e9-661ccaf8dd20 665ef2db-cd63-4086-81e9-************

3) WAF

개요

AWS WAF를 이용해 웹 공격을 차단하는 시스템을 구성합니다. Region은 us-east-1을 사용합니다.

과제 설명

많은 웹 애플리케이션은 사용자로부터 전달받은 값을 기반으로 데이터베이스 쿼리를 수행합니다. 이 과정에서 입력값에 대한 유효성 검증이 부족한 경우, 악의적인 쿼리문이 그대로 실행될 수 있으며 이는 SQL Injection (SQLi) 공격으로 이어질 수 있습니다. SQLi는 공격자가 데이터베이스 쿼리를 조작하여 인증 우회, 데이터 유출, 데이터 변경/삭제 등의 공격을 수행할 수 있는 심각한 보안 취약점입니다. WAF를 사용하여 입력값에 대한 유효성 검증을 받고, 악의적인 쿼리문을 차단시키도록 합니다.

1. Bastion

  • 동작 테스트를 위해 Default VPC에 EC2 Instance를 생성하며, Name Tag는 waf-bastion으로 생성합니다.
  • 채점을 진행하기 위해 SystemManager로 접근이 가능해야 하며, 접근 불가시 채점에 불이익이 발생할 수 있습니다.

2. App Server

  • EC2를 사용하여 App Server를 생성하며, VPC는 default VPC를 사용합니다.
  • 주어진 배포파일을 사용하여 App Server에서 Python 애플리케이션을 실행할 때, 서버가 종료되지 않도록 백그라운드에서 실행해야 합니다.
  • 또한 public IP를 할당해야 합니다.
  • App Server Name: wsc2025-app-server
  • Instance Type: t3.small

3. ELB

  • 위에서 생성한 App Server를 접근할 수 있는 Endpoint를 제공하기 위해 ELB를 생성합니다.
항목 값
Load balancer name wsc2025-waf-alb
Load balancer type Application
Load balancer Scheme Internet-facing

4. WAF

  • 애플리케이션에 존재하는 취약점을 찾아내고, 취약점에 대한 Rule 설정을 구성하며, 취약점을 공격하게 될시 403 Forbidden 에러가 떠야합니다.
  • WAF Name: wsc2025-waf

API

애플리케이션은 Python으로 개발하였으며 x86기반 시스템에서 빌드한 애플리케이션입니다. 실행시 TCP 5000 포트로 바인딩되며 어플리케이션 엔드포인트와 응답 결과값은 아래 테이블을 참고합니다.

Path Method Description Query String Example
/login GET 사용자 인증 name=admin&secret=x
/lookup GET 사용자 ID로 조회 id=1

4) Secure networking

개요

Network Firewall을 활용하여 VPC의 Egress 네트워크 트래픽을 제어하고 검사합니다. Region eu-west-1을 사용합니다.

과제 설명

1. VPC

  • Egress VPC는 인터넷 연결을 위한 Public Subnet, App VPC와의 통신을 위한 Peering Subnet, 그리고 Network Firewall만 위치하는 Firewall Subnet으로 구성하며, App VPC는 Private Subnet만 생성하고 외부와의 통신은 Egress VPC를 통해 방화벽(Firewall Subnet)을 경유하여 이루어집니다.
  • Subnet 이름 뒤에 영문은 AZ를 뜻합니다.

VPC

Name Cidr
wsc2025-egress-vpc 10.0.0.0/16
wsc2025-app-vpc 172.16.0.0/16

Subnet

Name Cidr VPC
wsc2025-egress-public-sn-a 10.0.0.0/24 wsc2025-egress-vpc
wsc2025-egress-public-sn-b 10.0.1.0/24 wsc2025-egress-vpc
wsc2025-egress-peering-sn-a 10.0.2.0/24 wsc2025-egress-vpc
wsc2025-egress-peering-sn-b 10.0.3.0/24 wsc2025-egress-vpc
wsc2025-egress-firewall-sn-a 10.0.4.0/24 wsc2025-egress-vpc
wsc2025-egress-firewall-sn-b 10.0.5.0/24 wsc2025-egress-vpc
wsc2025-app-private-sn-a 172.16.0.0/24 wsc2025-app-vpc
wsc2025-app-private-sn-b 172.16.1.0/24 wsc2025-app-vpc

2. Network Firewall

  • Egress VPC의 firewall 서브넷에 Network Firewall을 생성하며, 구성된 AWS Network Firewall은 다층 보안 전략을 통해 외부 인터넷으로 나가는 트래픽을 체계적으로 제어합니다. 이 시스템은 3단계 방어 메커니즘을 구현하고 있습니다.
  • 먼저, Stateless 규칙 엔진을 통해 모든 ICMP(ping) 프로토콜 트래픽을 차단하여 네트워크 스캐닝 및 ping 기반 공격을 차단합니다. 이는 네트워크 계층(L3)에서의 기본적인 보안 위협을 차단하는 첫 번째 방어벽 역할을 합니다.
  • 두 번째로 Stateful 규칙 엔진에서는 DNS 보안 강화를 위해 UDP/TCP 53 포트를 사용하는 모든 외부 DNS 쿼리를 차단합니다. 이를 통해 내부 승인된 DNS 리졸버만 사용하도록 강제하면서 DNS 탈취 공격과 데이터 유출 위험을 방지합니다. 또한 IP 직접 접속이나 HTTPS 암호화 트래픽을 통한 우회 접근까지 차단합니다.
  • 2개의 가용 영역에 걸쳐 고가용성으로 구성합니다.
  • Firewall Name: wsc2025-firewall

3. Bastion

  • 동작 테스트를 위해 App VPC에 EC2 Instance를 생성하며, Name Tag는 app-bastion으로 생성합니다.
  • 채점을 진행하기 위해 SystemManager로 접근이 가능해야 하며, 접근 불가시 채점에 불이익이 발생할 수 있습니다.

5) Serverless Inventory

개요

Skills Inc.는 서버리스로 자사의 재고를 관리하는 시스템을 구축하길 원합니다. Step Functions, API Gateway, DynamoDB 등을 사용해 별도의 컴퓨팅 서비스를 사용하지 않고 다음의 요구사항을 만족할 수 있는 시스템을 구축해야 합니다. Lambda를 포함한 EC2, ECS 등의 컴퓨팅 서비스의 사용이 불가합니다. 리전은 us-west-1에서 작업합니다.

과제 설명

1. DynamoDB

  • Table name: inventory
  • 아래 예제와 같은 record를 사전에 생성합니다.
    • {“name”: “balance”, “value”: 1000}
    • {“name”: “stock”, “value”: 100}

Scheme

Key name Type Description
name String PK
value Number

2. Step Functions

  • State machine name: inventory-state-machine
  • State machine JSON input
    • sales: 판매량, 1 ~ 30 사이의 자연수로 입력
    • ex) {"sales": 15}
  • State machine의 동작 구현

3. API Gateway

DynamoDB의 inventory 테이블 내용을 조회하기 위해 /inventory API를 제공해야 합니다.

항목 값
API Type REST API
API name inventory-rest-api
Stage name v1
  • /inventory API는 GET 요청만 지원하며 integration type은 AWS Service Proxy로 지정해야 합니다.
  • 만약 /inventory의 query string(item)으로 mysecret으로 시작하는 문자열을 받을 경우 HTTP status code가 403이고 body가 “403 Forbidden”인 응답을 반환하도록 합니다.
  • 요청 예시 (응답은 큰 따옴표를 출력하지 않아야 함)
Request Response Description
GET /inventory?item=balance 1000
GET /inventory?item=stock 100
GET /inventory?item=mysecret123 403 Forbidden HTTP status code 403
  • 채점 시 다음과 같은 URL로 HTTP 요청을 수행합니다. 또한 선수의 데스크탑이나 EC2 등 어디서든 접근 가능해야 합니다.
https://5yb12xiewd.execute-api.us-west-1.amazonaws.com/v1/inventory?item=balance
